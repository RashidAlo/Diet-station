DietStation Design Lab

Platform Mapping

DietStation is native-first: every material and behavior is designed for native iOS, and every one has a specified React/web fallback. This page is the pairing table — all values extracted from the shipping code, nothing invented.

The doctrine

Rashid's standing direction (2026-09-08): the native build is the design standard; the web twin replicates settled native design, with fallbacks only for iOS-only materials. When native and web disagree, native wins and the web catches up — never the reverse.

1 · Native iOS 26+
SwiftUI + real Liquid Glass APIs. The design standard — HomeScreenNative.swift is the reference implementation.
2 · Older iOS shell
Same WKWebView flows; the 1.6s handshake fallback restores web chrome where Liquid Glass twins can't render.
3 · React / web
Every other platform. The recipes on this page ARE the spec — not approximations to eyeball.

The chrome handshake (how a flow goes native)

Glass handshake v2, live on three flows: the web page pre-hides its own chrome and reports element geometry; the shell draws real Liquid Glass twins on top and confirms. On shells that never answer (iOS < 26), a 1.6s fallback restores the web chrome.

// web → native (on DOM settle, re-reported for async elements)
webkit.messageHandlers.ds.postMessage({
  t: 'glasschrome', flow: 'rewards', surface: 'dark',
  els: [{ id: 'close', x, y, w, h, r }]      // geometry per chrome element
});
// native → web: confirm twins (web keeps .ds-native-hidden on those ids)
window.DSNativeChrome(['close']);
// native → web: route taps back
window.DSChromeTap('close');
// guard: only in the shell (UA "DietStationLab"); 1.6s timer restores web chrome

// ── DS-CHROME-TOP — the canonical chrome line (named constant) ───────
// A device-dependent value can't be shipped as a number, so the DS owns
// the RULE and both codebases quote it (never re-derive it):
//
//     REAL_PAD  = max(28px, env(safe-area-inset-top) − 1px)
//     chromeTop = REAL_PAD + 9        // nav buttons, dual capsule, twins
//
// Web resolves it with a hidden probe div (env() only resolves in CSS);
// native computes max(28, safeTop − 1) + 9. On notched hardware the old
// shell constant (safeTop + 8) happened to agree exactly — the two only
// diverge at the max() floor: iPad (safeTop 24) +5, SE-class (20) +9.
// Agreement by coincidence on one device class is not agreement; quote
// the rule. Precondition for any future "twins go hit-test transparent
// and the web control underneath takes the tap": glass and control must
// coincide on EVERY device, which only this shared rule guarantees.

// TOUCH LAW (2026-09-10, after the meal-selector dead-zone forensics):
// a twin must NEVER create a touch dead-zone over scrollable content.
// - interactive twins hit-test ONLY inside the exact rects the web
//   reported for them (the els{} geometry) — never a larger container;
// - display-only twins (gauges, badges) pass ALL touches through
//   (isUserInteractionEnabled = false except real buttons);
// - the shell must not mutate the live scroll view mid-gesture (no
//   refresh-control re-seating, no bounce re-assertion) on chrome posts.

// ── MATCH A FLAG, NOT A CURVE (2026-09-11) ───────────────────────────
// Shell obligation: whichever side OWNS a motion must expose a
// SYNCHRONISATION PRIMITIVE for it. The other side never times against
// it. Any duration the far side picks is a guess that decays — wrong on
// the next device, wrong the moment the motion is interrupted
// mid-flight, and unmatchable in principle when it is a spring rather
// than a fixed ease.
//
// First instance — frame-exact twin teardown:
webkit.messageHandlers.ds.postMessage({ t: 'glasschrome', /* … */ instant: true });
// applies the WHOLE post inside a disabled-animation transaction, so an
// omitted twin is torn down on the exact frame the page takes its
// element back and the page owns the entire exit in CSS. Scope is the
// whole post: send it only where nothing else should animate to new
// geometry.
//
// COROLLARY: OVERLAP IS NOT SYNCHRONISATION. A fading twin sitting over
// a web copy drawing the same thing at the same rect LOOKS correct,
// passes review, and breaks silently the moment either side's timing
// shifts. Same failure family as a constant that agrees by coincidence
// on one device class (see DS-CHROME-TOP above): coincidence is not a
// contract.

// ── ONE GLASS, NEVER TWO (2026-09-11) ────────────────────────────────
// Overlay controls (the X, action capsules) are REAL Liquid Glass on
// iPhone and the CSS/WebGL fallback everywhere else. Which one you get
// is decided by the platform, once — the user must never see the
// handover, and never both at the same time.
//
//   in the shell : the web control must not paint for a SINGLE frame.
//   off-shell    : the web control is the real control, untouched.
//
// SUPPRESS ELEMENT-AGNOSTICALLY. A class applied to the elements that
// exist at parse loses the race to any control that is later REBUILT
// (rewards recreates its X per level theme) — the fresh one paints web
// glass until the twin confirms, which is Rashid's "starts with the web
// glass, then shifts into Apple liquid glass". Use a root-class rule
// over the same selectors instead, so it covers every element that
// exists now or is created later:
//   html.ds-chrome-native  { opacity: 0; pointer-events: none }
// and drop the ROOT CLASS in the no-twins fallback (iOS<26) — forgetting
// it leaves those shells with no control at all.
//
// NEVER REPORT A MOVING RECT. getBoundingClientRect inside a transformed
// ancestor returns the VISUAL rect, so geometry sampled while a sheet is
// springing up anchors the twin wherever the element was mid-flight, and
// it stays there ("it starts in the middle of the screen, not anchored
// to the top of the overlay"). Report after the motion that owns the
// element has ended (transitionend), never on a timer racing it — a
// timer that usually wins is the same coincidence in a third costume.
//
// SHELL SIDE — SILENCE IS PART OF THE PROTOCOL. The page's no-twins
// fallback fires only when the shell NEVER ANSWERS. That makes silence
// meaningful: a shell must not answer unless it can deliver what
// answering promises.
//   Never send a capability CONFIRM from a code path whose RENDERER
//   sits behind an availability gate the confirm does not share.
// Worked case: the app deploys to iOS 16+, twins render only under
// #available(iOS 26, *), and the confirms fired unconditionally — so on
// every pre-26 iPhone the page hid its own control, nothing replaced
// it, and the page's own fallback never ran BECAUSE the shell had
// already (wrongly) answered. Nine flows carry that handler; all of
// them would have shown no control at all. The clause above and this
// one are the same guarantee approached from opposite ends.
//
//        ANSWERING WRONGLY IS WORSE THAN NOT ANSWERING.

The lab gesture — three-finger tap-and-hold

One gesture summons the lab settings sheet on every prototype — web and native SwiftUI, TestFlight and browser. Canonical and singular by direction: three fingers, one tap, hold. The single-finger triple-tap-and-hold stays as the documented fallback for surfaces that can't produce three touches (mice, desktop, simulators).

Canonical recognizer 3 touches · HOLD 400 · SLOP 24
Rules (both platforms)
three SIMULTANEOUS touches down
held ≥ 400ms to fire — earlier release = no fire
≤ 24px/pt drift per finger during the hold; more = cancel (a three-finger drag never triggers)
a 4th finger cancels the sequence
on fire: present the lab sheet + light haptic (web vibrate(12) where available; native light impact)
never delays or blocks normal interaction
Fallback recognizer (pointer / desktop)
single-finger TRIPLE-tap-and-hold: taps on touch-down ≤ 550ms apart, 3rd held ≥ 380ms, ≤ 16px drift, second finger cancels — same sheet, same haptic.
web: both run together — threeFingerHold() primary, tripleTapHold() fallback (lab-shell.js, stamp 20260909a).
native: ThreeFingerHoldGesture is canon; triple-tap-hold is Debug-only.

Implementation notes (verified in lab-shell.js): passive listeners in the capture phase; POINTER events primary with touch fallback; mouse pointers excluded from the three-finger count; timing from hardware e.timeStamp, never processing time; a hold physically ≥ 400ms still fires on release even if jank starved the timer; a 600ms latch stops double-fires when both recognizers land. Native uses simultaneous gesture recognition, and a lab gesture never delays touches under a web surface: delaysTouchesBegan AND delaysTouchesEnded both false (the END default is true — it withholds a short swipe's touch-end up to 0.4s while the recognizer waits, eating quick sub-24pt flicks). Simulator ergonomics: a Debug-only two-finger hold alias (Option + click-hold) exists because macOS never hands the Simulator three touches.

Sheet content standard: top bar = Restart (fresh cache-busted reload) + Exit prototype (red), then User flow / Dev handoff links, then the flow's live controls.

Intent protocol — ds-nav

How flows interconnect from now on: a flow never navigates to another flow — it posts an intent and the hub presents the target. Specified here like a deep-link scheme; the grammar below is verified against the shipped router.

The grammar
Emit — flow → hub
parent.postMessage({
  t: 'ds-nav',
  to: '<flow-id>',  // flows.json id
  present: 'tab' | 'sheet' | 'push',
  context: { … }  // optional overrides
}, '*')
close: parent.postMessage({ t: 'ds-close' }, '*')
Announce — hub → flow
{ t: 'ds-router', v: 1 }
posted into the frame on every load, including tab swaps. A flow emits ds-nav ONLY after hearing this — without it, fall back to direct navigation. Lets both sides ship independently.

Presentation modes

tab — instant in-place frame swap, app tab-bar feel; stack depth unchanged.
sheet — slides up over the stack (also the coercion target: any unknown present value becomes sheet).
push — full-screen slide-from-right; dismisses with the matching slide-out.
ds-close — pops the posting frame and everything stacked above it, each with its own dismiss animation.

State policy & context

Reset on every transition (Rashid's call): the target always boots fresh, cache-busted with ?v=. Context is optional overrides only — never restored state — delivered on the target URL:

// target URL the hub builds:
<flow path>?v=<ts>&embed=1&from=<posting flow id>&ctx=<encodeURIComponent(JSON.stringify(context))>

// reading it inside a flow:
const q = new URLSearchParams(location.search);
const from = q.get('from');                       // who sent you here (may be null)
const ctx = q.get('ctx') ? JSON.parse(decodeURIComponent(q.get('ctx'))) : {};

// dead ends are SAFE: ds-nav to an unknown or offline flow id shows the
// branded "Coming in a later sprint" card — wire links to unbuilt flows freely.

Building a new flow? Wire its controls with data-act and one delegated listener from the first commit, and publish the semantic control map with its handoff — retrofitting it onto a finished flow costs far more than authoring it as you go, and until it exists the router regression run cannot drive your flow.

Native mapping: tab ↔ TabView selection, sheet ↔ .sheet/detents, push ↔ NavigationStack push — the intent grammar is presentation-agnostic so the shell can route the same messages to real containers.

Semantic control map — required in every handoff

A flow is only regression-drivable if a script can find its controls without reading its labels. Ours can’t be read: the house button splits its label across weight spans, so the text a human sees is not the text in the DOM. Verified in the shipping code — two flows, two different breakages:

The same button, two label shapes — neither is safe to match on
checkout — index.html:970
<span class="a">Guide</span>
<span class="b">me</span>
textContent → "Guideme"
a search for "Guide me" finds nothing at all
home — index.html:948
Guide <b>me</b>
textContent → "Guide me" — reads fine…
…until a matcher looks at innerHTML, or the
Arabic mode swaps the string entirely
The law
A CONTROL IS NAMED BY ITS CONTRACT, NOT BY ITS LABEL.
Labels are design surface. They get restyled, split across spans, shortened, and translated — DietStation ships an Arabic mode, so every label in the product is a moving target by design. data-act is the one name that holds still. Renaming a label is a design change; renaming an act is a breaking change.

Authoring rules

1 · One listener per flow. e.target.closest('[data-act]'), delegated at the phone root (checkout/index.html:1199). Not one handler per button.
2 · Every control that changes state or navigates carries an act. Decorative wrappers, scroll containers and pure-display rows do not — an act on a non-control is a lie in the map.
3 · Name the contract, in camelCase, and keep it stable. pickPlan, not blackBtn2. Restyle and retranslate the label freely; changing the act is a breaking change and gets announced to the lanes.
4 · Value-carrying controls declare their payload. The companion data-* goes in the map’s third column — including when it lives on an ancestor, as the steppers’ data-meal does.
5 · Author the map from the dispatcher, never grep it from markup. Checkout’s toPayment, pay and call are produced through template interpolation (data-act="${act}") and appear nowhere as literal strings — a grep of the markup finds 18 of the 21 acts and silently misses three, one of which is “Pay Now”.
6 · Cross-flow acts state the intent they emit. A regression run asserts the ds-nav message, not the screen that appears — the target flow may be unbuilt, and dead ends are legal.
