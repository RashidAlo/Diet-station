Composition

Native glass over web content. Most of the trouble in this lab happens at that boundary — this page is the contract for it, and the catalogue of every way it has actually broken.

What this page rules on

Rashid, 2026-09-13, on why this exists: the trouble is “when we try to do an overlap of liquid glass over the fallback web React stuff”, and the cost is double work and two lanes holding different understandings of the same surface. So composition is ruled here, published rather than argued per surface.

Process: a new native-over-web surface gets a short spec here before Shell and the feature lane build it. That ordering is the whole double-work fix — every failure below cost two lanes a round each, and none of them needed to.

The protocol

Both lanes, debugging from opposite ends of the bridge, reached the same conclusion about what to generalise: the protocol, not the renderer. The Shell lane’s count — a generic renderer would have prevented none of the failures below; a specced protocol would have prevented four of the five that reached Rashid. So the spec is the deliverable and the catalogue is its rationale.

The constraint — stated once so it is never re-argued
THE PAGE CAN NEVER DRAW ON TOP OF NATIVE GLASS. WHOEVER DRAWS THE GLASS DRAWS THE CONTENT INSIDE IT.
The shell’s material is a native layer above the WKWebView. There is no z-order, no opacity trick, no ordering of the two that puts page content over it.

So a spec naming a material and what sits under it is fine. A spec saying “web draws the text, native draws the container” is not implementable — not a trade-off, not a cost question. Platform constraint. It cost Rashid three separate reports in one day.

Diagnostic: blur is the discriminator. Crisp and blurred glyphs cannot both be foreground draws on one layer — if the text beside native text is pale and soft-edged, it is under the material, and no amount of tuning will lift it.

Ruling 1 — capability signalling

The first thing ruled here rather than described, because it is a protocol-design problem and not a documentation one. It cost four of Rashid’s reports, and both lanes arrived at the same rule independently — the Shell lane from the native side, Calendar & Meals from the page side. Convergence from two directions is the strongest basis a ruling in this lab has had.

Ruling — binding on every composited surface
AN ECHO SAYS “I HEARD YOU”, NEVER “I CAN DRAW IT”. AND A CAPABILITY FLAG SHIPS IN THE SAME COMMIT AS THE CAPABILITY.
1 · The confirm is a receipt. DSNativeChrome(ids, caps) derives ids from the payload, so it echoes back every id it received including ids it has no renderer for. Never infer capability from it.

2 · Capabilities are versioned numbers, not booleans. { scrubMotion: true, tileRows: 2 }, tested >= n, bumped and never re-used. A boolean cannot distinguish a build that announces a thing from one that has it.

3 · The bump lands in the same diff as the renderer — in EVERY relay that sends it. “Same commit” alone is not enough: build 48 satisfied it loosely, adding the cap to both confirm sites in one edit, and still lied, because only one of the two relays could honour it. The cap was also once added one build before the renderer. That build announces a capability and does not have it — it lies without anyone lying, and no measurement of the implemented build says anything about the announced-only one.

4 · Never confirm a capability from a relay that doesn’t share the renderer.

5 · A correctly-versioned cap REPLACES the per-build measurement. The rule once asked for “a measurement on a build in Rashid’s hands”, and a lane could not produce one — no device in that lane, and the shell’s primer passthrough is #if DEBUG, so a Release build cannot carry it. It doesn’t need to: because the bump ships with the renderer in every relay, a build that cannot draw cannot send the number, and the inference is sound without measuring each build. A rule that demands evidence a lane is unable to get will be quietly skipped.

6 · Until a signal satisfies 2 and 3, the web keeps the surface. A readable web surface beats a prettier unreadable one, and the fallback costs the user no install because it is page-side.

Applied to the open case: the resting date tile stays web-owned. That is not a concession pending a better build — under clause 5 it is the correct state for any surface whose handover gate cannot distinguish announcement from implementation, and it flips when a signal exists that ships with the capability, not when a build is measured. Generalised for future surfaces: the handover gate is part of the surface’s spec, and a surface whose gate can’t be trusted is specified as web-owned from the start rather than handed over and walked back.

The transferable half, from the Calendar & Meals lane and worth more than the clauses: a gate the lane that can SEE the failure can close in one line is worth more than a fix. The page can withhold the handover; only the shell can implement the renderer. Put the guard where the evidence is.

Ruling 2 — the date widget is one component, and it declares its slot count

First surface ruled before it was built, which is what the charter exists for. Rashid’s outcome — “make them one true native component” — was already settled; what came here was the shape. The page reported one element as two ids (tile and scrub) with two renderers, and the shell’s own log showed the handover as a swap. Mitigating a swap is not removing one.

Two candidate shapes were put up. A: make scrub the single component and express the resting square as a one-slot ladder in the vocabulary the shell already parses — eight empty slots, center 4.0 — needing no new field. B: carry an explicit slots: 1|9 and have the renderer size from it rather than from the width.

Ruling
SHAPE B. THE ELEMENT DECLARES ITS SLOT COUNT; THE RENDERER NEVER INFERS IT.
1 · A already means something else. The element contract states that '' is legitimate — the day-status map only arrives from the parent calendar frame, so a direct page load has none. Shape A makes eight empty slots also mean “resting, one slot”. One wire value, two meanings, and a receiver that cannot tell “I am at rest” from “I have no data”. That is failure 02’s family, arriving by a different door.

2 · A makes the renderer read a mode off animated geometry. The morph runs 52→370 continuously. Inferring slot count from width means choosing a threshold and sampling it on every tracked frame — which is failure 10 exactly, and failure 10 has already cost this very surface a round. A declared slots lets the sender latch the decision, which is what that rule asks for.

3 · “No new field” is worth least right now. A cap bump is already in this diff. A field added alongside it costs one line in two parses; the same field added later costs a migration. The one moment a field is nearly free is the moment the version is moving anyway.

Carry it as a count, not a flag. slots: 1 and slots: 9 extend to a five-slot week without a protocol change; isResting: true does not, and would need the same argument again.

The shape, as the Shell lane specified it

Three clauses, and the third improves the ruling rather than implementing it — my version fixed the mode-inference problem and left the '' overload only half-solved.

1 · slots is an integer count, not an enum

1 and 9 are today’s values; the renderer must not assume they are the only two, and lays out exactly slots slots. No thresholds anywhere.

2 · Carried in the shape of both posts, always populated

Not because it changes during a morph — it changes at arm, 1→9, before the width travels — but because a field present in one post’s shape and absent from the other’s is exactly the drift that cost the radius, the stateful on, and the tile’s rows (failure 04). Receiver rule: absent means “unchanged”, never a default, so an older page keeps working and a dropped key cannot silently reset the layout.

3 · The arrays are sized to slots

dates, dayNames and statuses have length == slots, and center indexes within that array — so at rest they are one-element arrays with center: 0, not nine-element arrays with eight empties.
This is what actually retires the '' objection. With fixed-nine arrays, '' would still carry both “no day-status map” and “not a real slot” — now with a slots field standing beside it rather than instead of it. Sized arrays leave '' meaning exactly one thing again, which is what the objection was about.

Two renderer changes clause 3 forces, named here so the page lane knows what moves underneath it and so they are tracked rather than discovered: the opacity ladder is a fixed nine-long table indexed by absolute index — at length 1 it would draw the resting numeral at 15% opacity — and the size taper is hardcoded around index 4. Both become distance from centre, and both land in the same diff as caps.dateWidget.
Neither is visible in the nine-slot case, which is precisely why they would have shipped broken had the arrays stayed fixed-length. A ruling that only changed the wire format would have hidden them; sizing the arrays surfaced them before anyone built.

Everything else in that spec stands. One id across both states; native draws glass and content in every state; the web element visual-only, keeping the gesture that arms the scrubber; the ladder vocabulary in every post, rest and track; height and top fixed with only width and radius moving, from one formula quoted by both sides. The migration is right too — while caps.dateWidget is absent the page keeps today’s two-id behaviour, so there is no window in which the date goes missing again.

One correction to the spec, and it is yesterday’s lesson one day old. The material line reads “.34 tint … inside the 0.07–0.2 band”. Those are not the same quantity. rgba(255,255,255,.34) is a CSS background alpha — the opacity of a white layer over what is behind it. tintOpacity is a shader mix factor: mix(color.rgb, gradientTint, u_tintOpacity), which blends the refracted colour toward a tint and does not touch alpha at all. The band governs the second and says nothing about the first. The material is unchanged either way, so nothing is blocked — but the two numbers must not be compared, and a spec that compares them will be built against. A number without its scope is an opinion with a decimal point in it, and this is what that looks like when it reaches a spec instead of a page.

On the evidence line: it asks for a measurement on the pilot on an installed build, which is more than Ruling 1 clause 5 requires — and correctly so. The cap makes the inference about capability sound without a per-build measurement; the first measurement of a new renderer establishes that it draws at all. Different claims, both worth having, and only the first is replaced by the version.

Ruling 3 — overlay controls are chrome, not sheet content

Rashid, on the meal-select overlay: the action bar “loads with web controls, and then they morph or they dissolve into the glass buttons. This is very not clean… I don’t want these workarounds in the middle of the experience.” And the shape he asked for: “they always sit at the top like this, starting from when the screen loads in, and they track in all different states of the overlay.”

The law
A HANDOVER THE USER CAN SEE IS A BUG. THE HANDSHAKE BELONGS BEFORE THE FIRST VISIBLE FRAME, OR AFTER THE LAST ONE — NEVER INSIDE THE EXPERIENCE.
Native-first is not “native once it settles”. A surface that begins as its own fallback and converts in view has shown the seam to the person the fallback exists to protect.

Why the seam exists, and why the obvious fix is already dead

The controls are inside the sheet (.nav is absolutely positioned within it), so they inherit the sheet’s entry motion. A twin can only be placed where the page says the element is — so while the element is travelling, the twin is chasing a moving target across a process boundary.

“Stream the geometry during the entry” is the obvious answer and it has been measured and killed. ·216 posted early and the twins trailed the rising sheet by ~78pt: the sheet climbs at over 4pt/ms, and a cross-process rect is a few frames stale by the time it lands. That is the bridge’s physics, not a bug to be tuned out — and it is why the lane’s current build waits for rest, which is precisely the seam being complained about. The previous state was worse still: the bar sat empty for a measured 934ms.

So the fault is not in the handover’s timing. It is that a control which must be native was built as content that moves.

Ruling
AN OVERLAY’S CONTROLS ARE SCREEN-ANCHORED CHROME OVER THE SHEET, NOT CONTENT INSIDE IT.
They are placed once, at the chrome line, and the sheet arrives underneath them. Their geometry does not move during the entry, so there is nothing to chase, nothing to stream, and no moment at which a web control has to stand in. This is the shape Rashid described — present from the first frame, in the same place, through every state of the overlay.

Clauses

1 · Decided before the first visible frame. Whether this device draws native controls is a session fact — the capability version is known from an earlier surface. Cache it and decide before the overlay opens. No capability handshake inside the visible window.
2 · On a capable shell the web controls never render. There is no morph because there is no web state to leave. This is the clause that answers the complaint: the seam is not badly animated, it is a seam that should not exist.
3 · Armed once per surface, not per state. Placed when the overlay opens and tracked continuously through partial, fullscreen and scrolled — never torn down and re-armed per state, which is failure 08’s territory. This is “they track in all different states”.
4 · Presented with content or not at all. Clauses 1–3 make this automatic: a static, pre-decided control is posted complete, so the empty glass square stops being possible rather than being fixed.
5 · The fallback is whole-life. On a device without the capability the web controls render for the entire life of the overlay and never hand over. One decision, made before the first frame, that never changes while the surface is on screen.

This extends failure 01’s rule — which lane draws it never changes mid-gesture — to never changes mid-surface. An overlay’s entry is a gesture in that sense.

Open, and it is Shell’s: a screen-anchored bar sits over the calendar’s red ground before the white sheet arrives beneath it, so the glass is momentarily tinting against saturated red rather than white — the 0.05 case in the material rules. Whether one tint reads correctly across that change, or the twin needs its tint to follow the ground, is theirs to measure. Nothing else in the ruling depends on the answer.

Status (2026-09-13): not shipped. Since ·217 the web bar rides the entry and hands over at rest, with ~80ms blank. Two motions comply: pinned (as written above: controls fixed at the chrome line, sheet rises beneath) or riding (twins travel with the sheet on a shell-owned entry, one clock). Rashid chooses the motion; Shell measures both. An amendment allowing the material to hand over at rest was proposed and declined, because that handover is the complaint this ruling answers.

Shell’s read (2026-09-13), scoped, for the choice:
Clause 1 needs no cache: capabilities are fixed per build, so the shell can inject window.DSNativeCaps as a document-start user script, present before any page script runs. That gives zero round trips inside the visible window. Not built. The invariant is unchanged and the mechanism is simpler.
Pinned hides a material handover. Meal selection posts surface: 'light' (.regular). Over the dimmed calendar before the sheet arrives, that material “goes milky-bright”, and Rashid has rejected that look before. Posting 'dark' during entry means switching material when the white sheet lands, which is a visible handover. The only way out is one material tuned for both grounds, which is untested and would be a design decision in its own right. Shell’s post-to-appear is 10ms (log timestamps, build 54 source, pilot); the page’s own post time is not measured.
Riding has no handover by construction. The web view and the twin layer are siblings in one native container, and twins sit in the web view’s own coordinates. So one native offset on that container, .timingCurve(.32,.72,0,1, .55s) from 103%, moves both on one clock, and the rest rects stay valid throughout. Cost: modest native work, not built. Page-side requirement: the meal selection sheet must stop animating its own entry. Unlike the calendar, that entry does run (measured, transitionend at 934ms). Scope it to the meal selection overlay: the calendar keeps its snap (·33), and riding there would reverse that decision.

What a strict ruling hides, and does not fix. The web tile’s numeral was painted under its own backdrop-filter glass for months. It was invisible because the native twin covered it at rest, and it only showed once ·217 let the web bar render during the entry (fixed ·224). Clause 2 makes web controls unseen in the shell, not correct. They remain the whole-life fallback (clause 5) and still need their own verification. Test them outside the shell.

What the web does underneath a twin

Three options, and picking the wrong one is failures 01 and 03. The choice is per surface and it is ruled here, not decided in either lane.

Visual-only — yields its pixels, keeps its gesture

The native side draws the surface; the web element still receives the touch. Needs an explicit pointer-events exception — and a newly built element does not inherit an older one’s exception, which is a whole round of “the square is inert” on its own. Suppress with a root class and descendant selectors so rebuilt elements stay suppressed (failure 05).

Inert — yields pixels and touches

The native twin is interactive in its own right. The web element is out of the way entirely.

No twin — the web keeps everything

The default, and the correct answer whenever the native side cannot draw the surface’s content. A readable web surface beats a prettier unreadable one.

Visual-only and inert are properties of the element, not of a class name — so the spec states which one applies per element, never per surface. The web-only fallback pairing is part of the same ruling: every composited surface names what it becomes where there is no native twin. A surface without that pairing is not specified, it is half-specified.

… and whether the native side consumes the touch

The other half of the same decision, and it is not a blanket rule — it is blanket for one class of surface and actively wrong for the other. Every native surface states, per element, whether it consumes. Never leave it to the default: SwiftUI’s default (hit-test only where there is interactive content) is wrong for the first class, and “consume because we drew it” is wrong for the second.

Native-owned chrome — consumes its whole silhouette

A bar, panel or control the shell draws entirely, with no web element beneath that anyone needs to touch. contentShape over the whole silhouette plus a no-op consumer, always. Without it the padding ring and rounded ends leak straight through — Rashid: “sometimes it taps items underneath the tab bar.” Measured A/B on one point: 56.5% of the screen changed without it (a flow opened), 0.5% with it.

A twin — consumes if and only if the element beneath is inert

Page element INERT (yields pixels and touches) ⇒ the twin must take the tap and route it back to the page. It is the only thing there; if it doesn’t consume, the control is dead.
Page element VISUAL-ONLY (keeps its gesture) ⇒ the twin must not hit-test at all — .allowsHitTesting(false), not a smaller contentShape. A twin that consumes here silently steals a gesture the page is still listening for, and the element goes inert while looking perfect. This is what the resting date tile requires: the page owns arm-on-touch, so its twin is non-hit-testing by construction.

Why this is load-bearing rather than pedantic
BOTH FAILURE MODES ARE INVISIBLE IN A SCREENSHOT.
A leaking bar looks perfect until a tap opens something behind it. A gesture-stealing twin looks perfect until someone tries to use the control. Neither shows up in the pixels, which is why both reached Rashid rather than being caught in review.

And the two columns are one decision stated twice: visual-only on the page side and non-hit-testing on the native side must be decided together. Mark an element visual-only while its twin consumes and the page’s pointer-events exception is pointless — the touch never reaches the webview to be excepted.

Written from the Shell lane’s struct rather than from either lane’s memory, so the two sides stop drifting. Channel is window.webkit.messageHandlers.ds; glasschrome is the rest post and chrometrack carries the same element shape per frame while a morph runs.

Material rules

Native-side, from the Shell lane. These are the ones a spec gets wrong by omission — each has produced a “there are two glass effects” report.

One element, not two shapes

A filled shape under a .glassEffect() gives two edges at slightly different sizes; a drop shadow adds a third. That is what “double container” looks like from the outside. Specify a plain fill at rest that morphs into the material when active — one element throughout.

Glass on glass is .clear with a .tint()

Two .regular surfaces stack their frost and read as two layers even when the shapes match exactly.

GlassEffectContainer merges siblings — it does not stack them

Wrapping a bar in one composites its glass into a single pass, which lifted a selection lens above the labels and refracted them into a smear. Use it only with glassEffectID unions.

A glass pill tints against its GROUND, not its component

The variable that drives the number is what is underneath. Measured across the native side: 0.05 over saturated brand red · 0.12–0.20 over a dark or coloured surface · 0.22 when the ground is itself glass, because glass on glass needs more tint to read at all. Brand-red tints sit at 0.15. Past roughly .5 white it stops being glass and becomes plastic.
The web layer runs lighter — 0.07 published, 0.14 shipped on nav glass in two flows, 0.2 the container default. That is a genuine native/web divergence, not an average; pair the two rather than quoting one range for both. A range quoted without its ground is unusable.
If a surface needs to read as opaque it is not a glass surface — give it a solid fill and say so.

Corners are .continuous, not .circular

RoundedRectangle(cornerRadius:) defaults to .circular and Apple’s own containers are continuous — visibly different at 52pt. A spec that says only a radius has under-specified the shape.

On a light ground, web cannot approximate the material at all

A translucent white panel over a white sheet is white: backdrop-filter has nothing behind it to refract and cannot reproduce edge response or specular. The page lane proved a web tile byte-identical to the native button (rgba(255,255,255,.34), blur(12px) saturate(1.6)) and it still read flat. Native, or accept that it reads as a panel — do not spend iterations closing that gap.

Three quantities, not one band
“TINT” NAMES THREE DIFFERENT NUMBERS ON THIS PROJECT. A TABLE OF THEM NEEDS THREE COLUMNS.
CSS background alpha — rgba(255,255,255,.34), the opacity of a white layer over what is behind it.
Shader mix factor — tintOpacity, used as mix(color.rgb, gradientTint, u_tintOpacity); it blends the refracted colour and never touches alpha. This is the quantity the 0.07–0.2 band governs, and it says nothing about the other two.
SwiftUI tint colour — .tint(.white.opacity(x)) handed to Apple’s material; neither an alpha over a background nor a mix factor.

A spec that puts a number from one column inside another column’s range will be implemented against. This was caught once in a page and once in a spec on consecutive days — the second time by comparing .34 to the band.

The spec, before anyone builds

Short on purpose — it is a ruling, not a document. One pass, from this page, before Shell and the feature lane start building.

SURFACE      which control, on which flow, in which state
TWIN         yes / no — and if no, stop here
DRAWS        who draws the content: native, or web. The same side must draw
             the glass AND the rows (failure 01) — there is no in-between
WEB DOES     per element: visual-only / inert / keeps everything
CONSUMES     per element, native side: whole silhouette (native-owned
             chrome) / consumes (twin over an inert element) / does not
             hit-test at all (twin over a visual-only element). Paired
             with WEB DOES — one decision, stated twice
FIELDS       every field, and EVERY construction and parse site — both
             relays, hub and pilot (failure 03)
GEOMETRY     the shared rule both sides quote (never two derivations)
MATERIAL     tint within 0.07-0.2, radius, and the web-only fallback pairing
CAP          the versioned number that gates the handover, and the diff it
             lands in
EVIDENCE     what measurement, on which surface, on a build in Rashid's
             hands, closes this

The last line is failure 02 written as a question. A spec that ends at “the shell will announce a capability” has not said how anyone will know it is true.

Instruments are part of the contract

The Shell lane’s point, and it earns its own card because it is the reason several of the failures above took multiple rounds rather than one.

Why a surface must announce itself
A SURFACE WITH NO INSTRUMENT PRODUCES EXACTLY THE SAME SILENCE AS A SURFACE WITH NOTHING WRONG.
Which is how two lanes verified the wrong screen three times in a row. Every relay logs under its own tag — DSCHROME(hub) versus DSCHROME(pilot) — so a reading names the surface it came from rather than assuming it. And every verification report states build, surface, and install method: a green result taken against a hot-reloaded dylib is not a result about the build in Rashid’s hands, and every green reading on the native path so far had been taken that way.

Four siblings, each bought with builds

Never claim an absence from a sampled window unless the window is proved to contain the event

“The native capsule never renders” was reported five times from frames sampled at 3–5s of recordings where the event was at 10–14s. Four fixes were built on it. Receiving side: ask how the window was chosen, and ask before building anything — asked first it costs one message; asked after the fourth failed fix it has cost four builds. And four failed fixes is evidence the diagnosis is wrong, not that the bug is deep.

When two lanes share a debug channel, each lane’s instruments must be proven on every surface the other lane serves

The page lane’s error beacon, bail log and capability receipt all worked on the hub and produced nothing on the pilot — because the pilot’s debug handler was schema-bound, logging three fixed keys and discarding the rest. Not forwarded and forwarded with its payload discarded have different fixes, and only the second leaves a misleading line in the log. Neither lane could notice: the sender can’t see that its beacon never arrived, the receiver can’t see that one was expected. Cheapest enforcement is a heartbeat — one debug line per page load naming the build, on every surface. It turns “my instrument is silent” from ambiguous into a positive test, and it comes with an ordering rule: if the heartbeat is absent from a surface’s log, nothing else the page reports on that surface can be trusted — check for it before reading anything else. Handlers must be shape-agnostic and tagged per surface, like the chrome lines.
What it cost the day it was found: every page-side instrument built that day was silently useless on the surface Rashid uses — the error beacon that had caught a module-level throw, the declined-handover log, the capability receipt. All worked on the hub; none existed on the pilot. It is also why that lane could not distinguish “the confirm handler was never called” from “the capability was below the threshold”, and correctly reported that it couldn’t.

An absence inside the container is not an absence if the data legitimately ends

The open strip measured two slots left of centre and three right — one present at x=363, nothing at x=39, and 39 sits well inside the container’s 15.7…386.3. It read as a lopsided visible range: the fifth instance of a known fault family, in exactly the place one had been predicted. Then the index arithmetic: the overlay was opened on day 16, so 16 is the range start, slot 1 is the day before the first selectable one, and the sender correctly pushes ''. A capture centred further along shows three each side from the same code.
The pixels were right and the inference was wrong. Sibling of the sampled-window law and the same shape as this card’s first line: the absence has to be earned, and earning it meant reading the range boundary rather than looking harder at the image.

Naming the file is part of “inspect the build”

On Xcode 26 a Debug build ships a launcher stub as the app binary and the real code sits in a .debug.dylib beside it. Grepping the stub returns zero for symbols that are definitely present — which reads exactly like “this build doesn’t have the feature”, and produced a confident wrong correction between two lanes. Release has no stub, so the rule inverts by configuration. Any instruction to verify a build by inspecting it must name the file. Measured on one bundle at one moment: grep -c tileRows returns 0 against the app binary and 4 against the .debug.dylib.
The general form, and it outranks the stub: a negative from a search is only as good as the place you searched. Confirm the instrument can find something you KNOW is present before you trust its absence. The lane that hit this had a zero for scrubMotion — shipped for days — sitting directly beside its zero for tileRows, and read the second as evidence while ignoring the first. A positive control costs one extra command and is the difference between a measurement and a guess.

This is the same shape as the laws on Price — a check that cannot fail, an audit that could not have found anything. Here it is a check that cannot say where it looked. Requiring the tag is cheap; the alternative is a correct measurement of the wrong screen, which is indistinguishable from success.

The catalogue — why the protocol says what it says

The rationale appendix. Every one of these happened here, most more than once, and each is the reason a clause above exists. Both lanes submitted their halves independently and the overlap is almost total — Calendar & Meals from the page side, Shell from the native side, arriving at the same rules from opposite ends of the bridge. The first two cost the most; the rest are grouped by kind.

01The number vanishes under the glass
Symptom
A native twin draws the surface, but text the web was drawing disappears — or arrives partly, one row present and two empty.
Cause
The shell’s glass is a layer above the WKWebView. Once the web hides its own content to avoid doubling, there is no way to put anything back over the material — the web cannot reach above it.
Rule
Whoever draws the rows must be whoever draws the glass. A surface is handed over whole or not at all, and it is not sent until the shell can render its content — there is no half-state, and which lane draws it never changes mid-gesture.
02The shell announces a capability it doesn’t have
Symptom
The handover gate passes, the surface is handed over, and the content is still wrong. Four rounds on the calendar tile, three of them reported by Rashid himself.
Cause
Two separate mistakes that look identical from the page. The confirm’s ids is derived from the payload — it echoes every id the page sent, including ids the shell has no renderer for. It means “heard”, never “can draw”. And a boolean capability cannot separate a build that announces a thing from one that has it: build 48 announced tileRows and drew only the weekday, build 49 announced the same and drew all three.
Rule
Never infer capability from the confirm. Capabilities are versioned numbers tested >= n, never booleans — bumped, never re-used, and the bump lands in the same diff as the code that honours it, in every relay that sends it. A measurement on one build is still not a property of the fleet: the lane measured 49, flipped the gate, and re-opened the hole for everyone still on 48.
03One field, two parses — “one row correct, the rest empty”
Symptom
A twin draws part of its content. One string arrives, the others are blank. Reads unmistakably as a page bug and isn’t.
Cause
There are two shell parses on two surfaces — the hub’s WKWebView and the native pilot’s overlay relay — and a field added to one and not the other is invisible until someone opens the other surface. Rashid uses the pilot. Every green reading either lane took came from the hub, whose parse was fine.
Rule
A field list is not specified until it names every construction site and every parse site, both relays. And a verification is not a verification until it names which surface it was taken on.
04Rest and track builders drift
Symptom
A twin is correct at rest and loses properties while moving — a radius stops morphing, a stateful control forgets it is on, rows vanish only during a gesture.
Cause
The resting post and the per-frame post were built by two different builders on each side. They drifted silently: the page’s track post dropped the radius, then a stateful on, then the tile’s rows — each one separately, each one invisible at rest.
Rule
One builder per side for the rest post and the track post — the same element shape, constructed once. A property that exists at rest and not in flight is not a variation, it is a bug with a long fuse.
05Doubling — two of the same control
Symptom
The web control and its native twin both paint. Briefly on arrival, or permanently on a surface that rebuilds.
Cause
Three different mechanisms, one symptom. (a) The web yielded by adding a class to elements that existed at parse time, so anything rebuilt afterwards came back unsuppressed. (b) Partial yield — the glass went but a hairline stayed, then a shadow, then a rim. (c) The yield decision not consulted at a transition: the exit stripped the hidden class and re-dressed the element, so the web surface reappeared on the landing frame and stayed until the next report re-hid it — “an abrupt square that keeps staying there.”
Rule
Yield with a root class and descendant selectors, never by touching the elements — it covers what exists and what is built later; and the fallback path must drop that class, or a shell that can’t draw the twin leaves the surface with no control at all.
A container is a container whether or not it blurs: the yielding layer renders nothing. One of everything by construction, not by careful subtraction.
And the ownership decision is consulted at every transition, not only at setup — setup-time correctness is not correctness.
06Ghost twins — glass stranded mid-flight
Symptom
The native glass sits in the wrong place — mid-screen, or where the surface was a moment ago rather than where it is.
Cause
Four mechanisms, one symptom — “a glass blob that forms down, gets stuck, then disappears.” (a) Geometry sampled while still animating: inside a transformed ancestor a rect read mid-spring returns the visual position. (b) The web surface un-hid ~120ms before the code stripping its armed geometry ran, so an armed-size empty box was briefly visible. (c) easeOutCubic parked the rect within a pixel of its target for ~170ms, so the capsule visibly sat at its destination before handover. (d) A closing class set width with !important while height was normal, so a rect measured after the class landed had its width already home — hence “forms down”.
Rule
Never report a rect that is still moving — gate on the owning motion finishing, with a timed belt, never a timer racing the animation. Whichever side owns a motion exposes a synchronisation primitive; the far side never times against it. Overlap is not synchronisation.
Hand over on the landing frame, in one statement; the thing taking the twin’s place must already be the right size; capture the from-rect before the closing class exists (see from: in the element contract — this is why). And prefer ease-in-out for a travelling handover: it keeps moving until it lands, so the frame it stops is the frame it is replaced.
07The tint kills the lensing
Symptom
The material stops reading as glass and becomes a coloured slab. Most visible on red surfaces.
Cause
Tint opacity pushed far past the working range. The shipped values are 0.07 published, 0.14 on the nav glass in two flows, 0.2 as the container default — an .85 slab is four to twelve times the top of that, and there is nothing left to refract through.
Rule
Composited surfaces tint inside 0.07 – 0.2. If a surface needs to read as opaque, it is not a glass surface — say so and give it a solid fill, rather than turning glass up until it stops being glass.
08Seams on re-arm
Symptom
The twin and the web surface agree on one device and are a few points apart on another — or drift apart after a surface re-arms.
Cause
Both sides derived the same geometry independently and agreed by coincidence. Coincidence survives one device class and not the next.
Rule
The design system owns the rule, not the number: both codebases quote one formula and neither re-derives it. Assert against the formula, never against the value it happens to produce on the device in front of you.
Same family, one element rather than two: if one property of an element follows the data, every property of it must. A twin drew a circle because its glass shape was hardcoded to a capsule while only the clip followed the reported radius — two properties of one element, one data-driven and one fixed, agreeing in exactly the case that was tested.
09Motion the measurement cannot see
Symptom
An animation runs in the browser and the twin never performs it. The inverse of 06 — nothing is stale, the motion was never sent.
Cause
A CSS keyframe, transform or filter moves rendered pixels while leaving getBoundingClientRect flat. The rect stream is built from the measurement, so the motion exists only in the stylesheet. A forming bounce ran 52→60→52, getComputedStyle showed it interpolating, and the shell’s per-arm max read 52 on every arm — accurate reporting of what was actually sent.
Rule
Any motion the shell must mirror has to be in the measured geometry, not merely in the rendered pixels — drive it from rAF writing the property the measurement reads. Corollary, and it cost four builds: “the instrument missed it” and “it was never there” want different fixes, and only the second was real.
10A threshold read live is read during the animation too
Symptom
A twin’s layout flips mid-gesture, or an exit re-lays-out while it is disappearing.
Cause
A mode-discriminating threshold (el.h < 64 choosing a metric set) sampled from the live rect. The entry’s overshoot crossed it going in; the collapse crossed it coming out.
Rule
Latch mode decisions on a value that cannot change mid-animation — the tallest rect of the arm, not the current one. And coupled constants across lanes (a 60pt peak against a 64pt threshold) are documented on both sides and retuned by neither alone.
11A guard defeated by an earlier call in the same frame
Symptom
A safety condition demonstrably present in the code has no effect. The lane asserts the failure is impossible while Rashid is holding it.
Cause
The tile’s suppression was gated on the shell’s confirm — but prehide() runs on every rest post, before any confirm, hiding every id in the map. The gate never got a chance to apply.
Rule
A guard is only a guard if nothing earlier in the frame already does the thing you are guarding against. When you add an id to a shared map, read every loop that iterates that map — not the one you are thinking about.
12Module state declared beside its reader instead of above its first caller
Symptom
No twins at all, no posts, no confirms. Reads unmistakably as the shell being broken.
Cause
var confirmed = {} placed next to the function that reads it, while that function is also called at module setup eighteen lines above. var hoists the declaration and not the assignment, so the setup call read undefined.tile, threw, and took the whole chrome module down before its API was assigned.
Rule
Declare module state with the module’s other state, above every caller. And note what the symptom was: total silence from the page, which is also what a healthy page looks like — a window error listener posting over the debug channel named it in one line. Instrument before diagnosis applies to the page, not only to the shell’s surfaces.
13A handover that declines to drive is invisible, not broken
Symptom
A morph doesn’t animate — the surface simply appears at its final size.
Cause
The page’s close interpolator can bail (no twin, not confirmed, already released) and hand the collapse to the web CSS — which in-shell is an element at opacity: 0. Nothing travels, and from outside that is indistinguishable from an animation that ran badly. The lane “fixed” the animation twice before discovering it was never running.
Rule
Any handover that can decline must say so, with the condition named — close BAIL el=… twin=… conf=…. A silent bail is a bug that presents as a taste problem.
14An exit inherited from a different return target
Symptom
The entry is smooth and the exit snaps — on the same surface.
Cause
The close was written when the surface returned to a small text label, so it rounded fully and shrank to a speck — both deliberate then. When the resting presentation became a 52pt squircle, those same tricks meant the capsule had to be replaced by the tile rather than becoming it, and three inherited numbers were all wrong for the new target.
Rule
When a surface’s resting presentation changes, its exit choreography is re-derived, not inherited. Entry and exit are the same move in opposite directions — same duration, same curve, the rounding travelling with the size so they land on the same frame.
Sibling: a derived offset dies silently when either of its inputs changes. A tile sat at --top-pad + 5px, the number that centred a 52pt square against 44pt buttons; the buttons became 52 and nothing failed loudly — the square just rode 4pt high with equal height and a different line.

Numbers 03, 04 and 06 are the glasschrome laws already carried on Platform Mapping — restated here as failures rather than as protocol, because a lane hits the symptom first and looks for that. 01 and 02 are new, from the calendar tile rounds.

Where the boundary sits today

Live state, not a ruling — it moves, and these lanes are mid-flight. Recorded so a reader knows which side of the line they are on.

The shell currently holds around 320 lines of calendar-specific SwiftUI — dates, day names, statuses, month label. That is not drift to be corrected: crisp text cannot be drawn by web content under Apple glass, which is failure 01 stated as a constraint rather than a bug, and Rashid has accepted it. It is also exactly why these rules matter — that boundary is where the two lanes meet, and every failure above happened within a few points of it.

Ruling 2 is built, shipped and measured. The date widget is one component across both states — verified at source: tile is gone from the page entirely, one dateEl() builder feeds the rest post and the track post so they cannot diverge, slots is derived as a count (e.slots = e.dates.length), and at rest the arrays are one element long with center: 0. Measured on the pilot on an installed build: one id across the whole gesture, fade symmetric by distance (75/74 at one step, 134/134 at two), pitch 54.0 exactly, centre slot at 201.0 against a container centre of 201.0, and the close landing on 52 in 24 frames. The swap is gone rather than disguised.

Four renderer faults were surfaced by the pre-build pass and all four are fixed — including two that appeared after the renderer was called done: a selection colour that drew the resting numeral red, and the hardcoded capsule above. Worth keeping as a note on what “done” means: the lane that implements a renderer is not the lane that can see it fail, which is Ruling 1’s point arriving one level down.

The contract and the brake are not redundant, and one is not a reason to delete the other. A versioned cap protects against a build that announces what it cannot do. It does nothing about a capability that is correctly announced and then breaks — a regression inside a shipped renderer — which is what the flag closes, in one page-side line, with no build and no wait. The contract prevents the lie; the flag survives the mistake. Keep both.
