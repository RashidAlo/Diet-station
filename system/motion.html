Counting numbers

When a displayed value changes, it counts over — it never jumps. The home screen's calorie and macro readouts set the standard: scroll the meal strip between days and the numbers roll to their new values. Tap a day below to feel it.

These are two different animations

Not one effect with two implementations — the platforms animate different things, and it is worth knowing which one you are looking at.

iPhone — the standard

.contentTransition(.numericText(...)) animates the digits, not the value. Each digit position is its own column that slides vertically to its new glyph, so:

· Unchanged positions never move. 1200 → 1250 moves the tens column alone; the rest sit perfectly still.
· No in-between number is ever shown. Going 1200 → 2025 it never displays 1677 — there is nothing to read mid-flight, only glyphs in transit.
· Direction is semantic. .numericText(value:) infers roll direction from the numbers; the days dial forces it with .numericText(countsDown: true).
· Timing comes from the surrounding animation, not from the transition — the kcal capsule rolls under .spring(duration: 0.55) keyed to the meal strip's day. A spring, so it settles rather than stopping.
· Digit-count changes (1200 → 940) slide a column in or out at the edge instead of reflowing the text.

The system renders it — which is why there's blur

This is not a transform you compose. .contentTransition declares intent, and SwiftUI renders the transition itself at the glyph level — which is why the effect carries something a CSS odometer doesn't: a glyph in transit is blurred and faded as it travels, softening at speed and resolving crisp on arrival, while a digit that isn't changing stays perfectly sharp throughout. That optical treatment is what makes it read as a physical counter rather than sliding tiles, and it is the part you cannot get from translation alone.

You own the timing; the system owns the choreography. The curve comes from the enclosing animation — ours is .spring(duration: 0.55) — and the per-glyph travel, blur and fade come from the platform. That split is also why the effect adapts on its own to font, weight and Dynamic Type without ever being retuned, and why it degrades gracefully to a plain crossfade in contexts where the system can't render the full transition.

In practice it needs: the value change to happen inside an animation context (withAnimation or .animation(_:value:) keyed to whatever drives it); Text(verbatim:) if you don't want an Int localised into “1,200”; and .monospacedDigit() so the number can't change width mid-roll.

What the HIG asks of it

Apple's motion guidance, applied to counters:

· Motion should clarify a change, not decorate it. A counter earns its animation precisely because it shows one quantity becoming another — which is the same test as Count-or-snap below. Animating between unrelated numbers is decoration, and reads as a slot machine.
· Keep it brief. A count long enough to watch is long enough to make the interface feel slow; ours settle in roughly half a second.
· Honour Reduce Motion. When someone has it enabled, the roll should give way to a plain value change or a simple crossfade. This is an accessibility requirement, not a nicety.
· Never let the layout move. Proportional digits change width as they roll and shove the surrounding text; monospaced/tabular figures are mandatory for any number that animates.

Source: Apple's HIG — Motion and the ContentTransition API reference.

Two gaps in our shipped code, found writing this up: neither the native screen nor the web twin currently checks Reduce Motion — the counters roll regardless of the setting, on both platforms; and the native numbers don't carry .monospacedDigit(), so a roll that crosses a narrow digit can nudge the layout. Both are small fixes in the owning lanes (native: @Environment(\.accessibilityReduceMotion) guarding the animation, plus the modifier; web: a prefers-reduced-motion branch that sets the value directly). Flagged, not fixed — they're Home's file.

Web — the fallback

The web twin animates the value and repaints the whole number: 420ms, cubic ease-out (1 − (1−p)³), rounded each frame. So every intermediate frame is a real, readable number, every changing digit churns at once, and the motion lives in the quantity rather than in the glyphs. Its own virtue: the count starts from the currently displayed number, not the previous target, so interrupting mid-count continues from what the eye is actually seeing instead of snapping backwards. A light haptic fires once at the trigger, never per digit.

Two smaller divergences, both already handled in the shipped code: native uses Text(verbatim:) so an Int doesn't localise to “1,200” where web shows “1200”; and both sides need tabular-nums so digits don't reflow while they move.

Open question for Rashid: the web fallback approximates the iPhone effect but does not reproduce it. Matching it properly means building a real digit-column odometer on the web (each position its own sliding column, unchanged columns held still) — buildable, but a genuine piece of work rather than a parameter change. Until that's ruled on, iPhone is the reference and web is an acknowledged approximation, not a bug to be quietly "fixed" either way.

Count or snap

Count when the value is the same quantity moving — the same day's calories recalculated, a macro total as meals change, a countdown of remaining days. Snap when the number is a different thing entirely: a new item's price, an ID, a list index. Counting between unrelated values reads as a slot machine, not a measurement.

Sibling: the ticking countdown
The days-left dial uses a deliberately different motion — it steps down one whole unit at a time with a light haptic per tick, while its arc eases to the final fraction underneath. Discrete units that a person would count out loud tick; continuous quantities roll.
step .07s linear, 75ms between ticks · arc .9s ease-out · haptic: light impact, intensity .4, per tick

Canonical implementation: countTo(el, to) in home/index.html — one shared function driving calories and all three macros, matching native's thinPair. (It previously counted only the calories while C/P/F snapped; brought in line when this pattern was written up, so web and native now roll together.)

// HIG parity the web owes: honour Reduce Motion, keep figures tabular —
//   if (matchMedia('(prefers-reduced-motion: reduce)').matches) {
//     el.textContent = to; return;           // plain change, no roll
//   }
//   CSS: font-variant-numeric: tabular-nums
function countTo(el, to) {
  const from = +el.textContent;          // on-screen, not the last target
  if (from === to) return;
  const t0 = Date.now();
  clearInterval(el._count);              // a new count replaces the old
  el._count = setInterval(() => {
    const p = Math.min(1, (Date.now() - t0) / 420);
    el.textContent = Math.round(from + (to - from) * (1 - Math.pow(1 - p, 3)));
    if (p >= 1) clearInterval(el._count);
  }, 28);
}
